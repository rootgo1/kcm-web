# 직원 로그인과 매장 고객·상담 요약 조회

2026-10-07 — `fix/staff-customer-read`

## 구현 범위

고객관리의 저장 고객 패널은 직원 로그인을 확인한 뒤 최근 고객과 저장 상담 요약을 표시합니다. Supabase Auth의 이메일·비밀번호 로그인을 사용하며, 앱에서는 회원가입·비밀번호 변경·직원 권한 부여를 제공하지 않습니다.

브라우저에는 무작위 조회 세션 쿠키와 마스킹된 직원 식별정보만 전달합니다. 쿠키는 HttpOnly/SameSite=Strict/Path=/이며 운영 HTTPS에서는 Secure와 `__Host-` 이름을 사용합니다. 비밀번호·Supabase access/refresh token·키는 응답이나 브라우저 저장소에 보관하지 않습니다. access token은 서버 메모리에만 있고 refresh token은 보관하지 않습니다.

세션은 최대 30분 또는 Auth 토큰 만료 시각 중 빠른 시각까지 유효합니다. 서버 재시작 후에는 다시 로그인합니다. 매 조회마다 Auth `GET /auth/v1/user`와 관리자 지정 매핑을 검증합니다. 기존 직원 연결은 현재 DB의 직원·매장 소속을 확인합니다. 별도 조회 계정은 명시된 `customers:read` 권한과 현재 DB의 매장 존재를 확인하고, 직원 ID 없이 ‘조회 계정’으로 표시합니다. Auth 검증 실패 또는 통신 장애 시 고객 자료를 조회하지 않습니다. 사용자 수정 가능한 `user_metadata`는 권한 판단에 사용하지 않습니다.

운영에서 새로 허용하는 경로는 다음 두 GET뿐입니다.

- `/api/data/customers`
- `/api/data/customers/:customerId/consultations?limit=5` (최대 20)

매장은 서버의 `KCM_DEMO_STORE_ID`로 고정합니다. 고객이 속한 상담도 같은 매장인지 기존 provider에서 확인합니다. 이름·전화번호 마스킹, 개인정보 미동의 차단, 요약 내 연락처 제거와 원문 제외 정책을 보존했습니다. 예약·일반 브리핑·고객 지정 체감가 등 다른 개인자료 경로의 기존 공개 환경 제한은 유지합니다. 상품 화면의 고객 선택기는 운영 직원 모드에서 조회하지 않습니다.

로그아웃·만료·권한 실패 시 고객 패널을 해제하여 선택 고객·검색·이력 상태와 진행 중 조회를 제거합니다. 창을 다시 볼 때 권한을 재확인합니다. 이전 계정의 늦은 응답은 다시 표시되지 않습니다. 로그아웃 통신 실패 시에도 자료를 닫고 세션 종료 재시도만 허용합니다.

## 운영 적용 전 필요한 관리자 설정

1. 현재 DB와 **같은 Supabase 프로젝트**에서 조회할 직원 Auth 사용자를 확인합니다. 이메일 확인 완료, 비익명 계정이어야 합니다. 새 비밀번호 입력·설정은 직원 또는 관리자가 직접 수행합니다. 비밀번호와 실제 키를 대화/소스에 전달하지 않습니다.
2. 관리자 승인을 받은 Auth User ID를 운영 매장에 연결합니다. 기존 직원 연결은 `employees.id`, `employees.store_id`를 지정하고 매 조회 소속을 검증합니다. 별도 조회 계정은 직원 개인정보를 만들지 않고 `storeId`와 정확한 `scope: customers:read`를 지정합니다. 두 형태의 혼합·알 수 없는 키·다른 scope·중복 UUID는 거부됩니다. 승인된 계정만 추가하며 운영 매장과 정확히 같아야 합니다.
3. 서버 환경의 `SUPABASE_AUTH_PUBLISHABLE_KEY`에 해당 프로젝트의 `sb_publishable_…` 공개 키를 설정합니다. 기존 `SUPABASE_READ_KEY`와 분리하며 secret/service-role/legacy JWT는 Auth 키로 허용하지 않습니다.
4. `STAFF_READ_ACCOUNTS_JSON`에 승인된 매핑 배열을 설정합니다. 아래 값은 형식 예시이며 실제 계정이 아닙니다.

```json
[{"authUserId":"11111111-1111-4111-8111-111111111111","employeeId":"employee_001","storeId":"store_005"}]
```

기존 직원으로 연결할 대상이 없는 별도 조회 계정의 형식 예시입니다. 두 예시는 같은 UUID를 사용하는 대안이며 함께 넣지 않습니다.

```json
[{"authUserId":"11111111-1111-4111-8111-111111111111","storeId":"store_005","scope":"customers:read"}]
```

5. 승인된 환경에 코드를 배포하고 서버를 재시작합니다. 설정 누락·형식 오류는 기본 차단이며 기존 DB 스키마/RLS/권한을 자동 변경하지 않습니다. 기존 읽기 키에 최소 SELECT 권한과 RLS 접근이 있어야 하며, 이번 변경은 이 권한을 늘리지 않습니다.
6. 승인된 직원이 고객관리에서 직접 로그인하여 목록→고객 선택→실제 저장 요약을 확인하고 로그아웃합니다. 미승인 계정·다른 매장 직원은 거부되는지 확인합니다. 운영 로그에는 비밀번호·토큰·응답 원문을 기록하지 않습니다.

권한 회수는 매핑 제거 후 서버 재시작 또는 해당 Auth 계정 차단/삭제로 처리합니다. 기존 직원 연결은 DB 직원 매장 변경도 매 조회 반영합니다. 매핑 변경은 서버 재시작 뒤 반영되며 모든 조회 세션도 폐기됩니다. 실제 Auth 계정 차단·소속 변경 반영은 운영 적용 후 확인 대상입니다.

## 검증 및 제한

- 합성 데이터를 사용한 Auth 모듈 34개, HTTP 통합 7개, 프런트 계약/세션 경합 23개를 포함하며 최신 고객 화면과 통합한 전체 검사 결과는 STATUS.md에 기록합니다.
- 프런트·서버 타입 검사, production build, 독립 HTML 재생성 완료.
- 실제 직원 계정/환경값/운영 DB 변경, 권한 부여와 운영 배포는 아직 수행하지 않았습니다. 실제 로그인→실제 저장 기록 조회는 운영 설정 이후 검증해야 합니다.
- 이 기능은 **저장 고객 조회 전용 로그인**입니다. 기존 샘플 프로필·전체 업무 화면 로그인과 별개이며 기존 공개 실시간 통화/SSE와 시연 고객 브리핑의 범위를 변경하지 않습니다. 조회 계정은 직원 사칭·직급·예약 업무 권한을 부여하지 않습니다. 이 경로의 추가 인증과 n8n 웹훅 인증은 별도 후속 범위입니다.
- Supabase에 확인된 MFA 인증 요소가 있는 계정은 추가 인증 화면을 지원하지 않아 로그인·조회를 거부합니다. 로그인 후 MFA가 등록된 경우에도 다음 조회에서 차단합니다. CAPTCHA가 요구되면 Auth 오류로 거부됩니다. 필요하면 관리자 정책을 유지한 채 MFA/챌린지 지원을 별도로 구현해야 합니다.
